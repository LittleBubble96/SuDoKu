# 数独埋点事件与属性

更新日期为 2026-11-11。本文对应当前代码，覆盖启动、登录、对局、提示、说明页、奖杯、广告、领奖及首页入口。全部自定义事件走 `GameSDK.SDK.ReportEvent`，Bi 类只声明字符串和整数属性（int/long），不使用枚举或 bool 参数。微信接口要求字符串字典，整数在基类统一转为十进制字符串，状态标志使用整数 `0` 和 `1`。

## 当前统计口径

- 对局 ID 在新开、重开时生成，恢复沿用。旧存档补 ID，不补算历史开局或通关事件。暂停、回首页、退出重进和切换每日挑战均不算弃局。未完成普通题被替换、未完成题重开才上报放弃。重玩同一道题的新对局仍有独立 ID。
- 每次玩家通关最多上报一次完成，读档和重复保存不重发。填错会影响无误成绩，使用提示仍允许无误。GM 通关和填题与正常操作使用同一统计流程，计入成绩、连胜、任务、奖杯、广告解锁和埋点，不再发送排除事件。
- 奖励在管理器修改余额、保存领取标记后上报。完整观看广告只产生广告结果，只有实际发奖成功才产生 reward_claimed；广告跨日、窗口关闭、对局已切换时可能有 completed 而没有广告领奖事件。
- 奖杯以配置 ID 和持久化奖杯记录去重。自然达标新增、读档补发都会上报，已有记录不重复上报。事件的 completed_days 统计不同挑战日期，包含 GM 完成的挑战。GM 直接授予奖杯仍使用原有调试入口。
- Banner 解锁读取 `AdIds.BannerUnlockWins`，当前为 **1 道不同普通题**。插屏读取 `AdIds.InterstitialUnlockWins`，当前为 **2 次通关**，普通局和每日挑战一起计算。这些数值来自当前配置，本次埋点接入沿用它们。激励视频当前没有通关解锁门槛，保持各入口主动触发。
- Banner 从原生展示成功开始计时，每次连续可见生成 exposure_id。按 **满 30 分钟分段上报，隐藏时补剩余量** 实现。后台、暂停、弹窗、其他广告、离开对局和通关会停止计时。37 分钟的连续展示生成 1,800,000 毫秒与约 420,000 毫秒两段。再次显示使用新 exposure_id。
- 插屏在游戏初始化时后台预加载，入局仅尝试展示已经就绪的广告。未就绪直接跳过，之后加载成功不会追着当前对局补弹。原生显示成功才计曝光，正常关闭使用 closed。
- 首页当前“攻略”入口继续使用稳定标识 game_club；显示文案变化不改变分析标识。底部每日挑战页签与首页卡片都属于 daily_challenge。

## 事件类与复用方式

22 个自定义事件各有一个具体类，统一继承 BiEvent。类定义集中在 `Assets/GameScripts/GameSDK/BI/BiEvents.cs`，BiManager 初始化并缓存每类一个实例。原生游戏启动继续使用微信的原生接口。

```csharp
BiManager.OtherGameNavigateResult.SetData("xunzi", "success").Report();
// 失败时传入该事件声明的条件参数：
BiManager.OtherGameNavigateResult.SetData("xunzi", "fail", "sdk_error").Report();
```

每个 Bi 类声明固定 EventName、明确的 string/int/long 属性，以及自己的 SetData 方法。SetData 内部清空复用字典，设置全部属性，再写入该事件需要的键；条件属性恢复默认值并按条件省略，避免上一次内容残留。业务代码只传参数并 Report，不在外部追加字典字段。基类只保留字典、整数转字符串和上报入口。

SetData 与 Report 在主线程连续调用，不跨 await。广告请求与 Banner 曝光保存原对局的整数和字符串快照，异步回调取原值传入对应 Bi 类，不保存可变字典或 Bi 对象状态。

当前微信适配器在调用中同步序列化 Data，编辑器同步读取。接口返回后可立即复用同一个 Bi 实例。正常发送直接把 EventName 和 Data 交给 SDK，不创建快照、不经过队列。未登录、已有积压或同步发送抛错时才复制 EventName 和 Data；事件名和字典值都是不可变字符串，复制字典即可隔离后续 SetData。

延迟节点及其字典成功发送后清空并回收到内部缓存，积压增加到历史峰值之外时才创建新节点。补发另用一个复用发送字典，隔离待重试快照与平台发送参数。平台接口约定同步消费且不修改调用者 Data；若以后更换为异步持有参数的 SDK，应在该适配器边界复制。

## 性能调整与发送机制

- 正常登录且没有积压时直接调用平台接口，不分配事件节点，不复制字典，也不受补发预算限制。
- 仅延迟事件进入快照队列；已有积压时维持 FIFO，每帧最多补发 8 条。新增事件不会重置该预算。空队列直接返回。
- BiManager 复用 22 个事件实例及各自的字典。字典预分配容量，不创建临时参数字典；整数转换与微信 JSON 序列化仍有必要的字符串开销，不承诺零分配。
- Banner 未展示时计时器直接返回。展示期间只检查单调时钟，只有曝光、30 分钟分段、停止可见这些节点填写事件数据。
- 激励与微信广告的详细 Trace 仅在编辑器或 Development Build 编译，正式包跳过这些日志及其参数字符串构建。Release 也不再为纯加载日志生成 load GUID。
- 常用的单广告 EnterPage/ExitPage 增加单字符串入口，避免 params 数组与 HashSet。State 相同不重复广播界面刷新。
- 持久化字段沿用 roundId、暂停普通题的 progressPercent 快照、结算 roundId，以及广告解锁位标记 telemetryAdUnlockFlags，复用现有 Unity/WX 缓存。

## 验证与边界

临时验证工程执行实际 SdkSession、AdTelemetry 和全部 Bi 类代码的 113 项检查，覆盖正常直发、字典原引用传递、延迟队列限流与 FIFO、登录前快照、失败重试、条件字段清理、全部事件的参数类型、广告去重和 37 分钟 Banner 分段。实际对局及奖励管理代码另有 39 项统一 GM 检查，覆盖 GM 计入已玩、通关、无误、连胜和分数，任务与奖杯触发、宝箱领取、重复回调去重、重启恢复、旧计数迁移、GM 辅助后使用提示及放弃事件。

Player、Editor、Release 三种配置下的 GameSDK、GameLogic、Assembly-CSharp 共 9 次编译检查通过。

这些验证使用替代的缓存、平台发送端和 UI 事件桥；没有伪造真实微信曝光。最终编译检查与未完成的真机验证以交付说明为准。

队列最多保留 512 条，登录超时或网络异常期间可能积压；满队列仍沿用原行为丢弃新增事件。发送失败的队首有限重试，三次同步异常后保留等待手动重试。微信 ReportEvent 无本项目可用的服务端接收确认，返回 true 只表示已调用平台接口或已保留延迟快照，不代表微信服务端确认接收。解锁及奖杯去重标记跟随业务存档，当前没有额外的持久化事件发件箱。

进程被直接强杀时，内存队列及尚未补报的 Banner 尾段可能丢失。历史普通题通关记录没有 GM 来源明细，解锁计数沿用现有记录；已有的聚合统计不倒推无法还原的历史逐局成绩。旧结算没有历史 round_id 时保留实际领奖信息，不编造对局关联。
